# SELAH 2.0 주간 점검 리포트 (2026-06-04)

> 이 문서는 개발자가 아니어도 이해할 수 있도록 쉬운 말로 정리했습니다.
> 각 항목에는 **무엇이 문제인지 / 왜 중요한지 / 무엇을 하면 되는지**를 함께 적었습니다.
> 이번 리포트에서는 **코드를 고치지 않았습니다.** 점검과 제안만 담았습니다.

## 1. 한눈에 보는 요약

SELAH는 AI 기반의 기독교 정서 지원 · 성경 묵상 앱입니다.
(기술적으로는 Next.js 웹앱 + Supabase 데이터베이스 + Anthropic Claude AI + 모바일 앱 빌드)

전반적으로 **구조는 잘 잡혀 있고**, 로그인·개인정보 보호(사용자별 데이터 격리),
알림 기능 등이 안정적으로 만들어져 있습니다. 다만 **출시·운영을 앞두고 꼭 챙겨야 할
"안전장치"가 몇 가지 비어 있습니다.** 특히 아래 3가지는 우선 처리할 것을 권합니다.

| 우선순위 | 한 줄 요약 |
|---|---|
| 🔴 **긴급** | 비밀키(API 키 등)가 실수로 외부에 노출될 수 있는 설정 누락 (`.gitignore` 없음) |
| 🔴 **긴급** | 위기(자살·자해) 감지가 한국어·영어에서만 작동 — 나머지 5개 언어 사용자 보호 공백 |
| 🟠 **높음** | AI 사용량·이미지 크기에 제한이 없어 비용 폭증·악용 위험 |

## 2. 보안 점검

### 🔴 2-1. 비밀키가 실수로 공개될 위험 (`.gitignore` 파일 없음)

- **문제**: 코드 저장소에 `.gitignore`라는 "올리면 안 되는 파일 목록"이 **존재하지 않습니다.**
  그런데 안내 문서(`README_GITHUB_NETLIFY.md`)에는 "`.gitignore`에 제외 처리되어
  있습니다"라고 적혀 있어, **문서와 실제가 다릅니다.**
- **증거**: 원래는 올라가면 안 되는 빌드 임시 파일(`tsconfig.tsbuildinfo`)이
  이미 저장소에 올라가 있습니다. 즉, 걸러주는 장치가 없다는 뜻입니다.
- **왜 중요한가**: 이 상태에서는 비밀번호·API 키가 담긴 `.env.local` 파일이
  **실수로 통째로 공개 저장소에 올라갈 수 있습니다.** 한번 올라가면
  키가 유출되어 요금 폭탄·데이터 접근 사고로 이어질 수 있습니다.
- **무엇을 하면 되나**: `.gitignore` 파일을 추가해 `.env.local`, `node_modules`,
  `.next`, `*.tsbuildinfo` 등을 제외 처리하고, 이미 올라간 임시 파일은 정리합니다.

### 🟠 2-2. AI 호출량 제한이 없음 (비용·악용 위험)

- **문제**: 로그인한 사용자가 채팅(AI 응답) 기능을 **횟수 제한 없이** 사용할 수 있습니다.
- **왜 중요한가**: 한 사람이 자동화 도구로 수천 번 호출하면 **Anthropic AI 사용료가
  순식간에 크게 늘어날 수 있습니다.** 출시 후 비용 사고의 가장 흔한 원인입니다.
- **무엇을 하면 되나**: 사용자당 "분당/일당 메시지 한도"를 두는 것을 권합니다.

### 🟠 2-3. 첨부 이미지 크기 제한이 없음

- **문제**: 채팅에 이미지를 첨부할 때 **용량 상한이 없습니다.**
- **왜 중요한가**: 아주 큰 이미지를 반복해서 보내면 서버 부담과 AI 비용이 커집니다.
- **무엇을 하면 되나**: 이미지 최대 크기(예: 5MB)를 정해 초과 시 거절합니다.

### 🟡 2-4. 알림 예약(크론) 비밀값이 주소(URL)로도 전달됨

- **문제**: 정해진 시간에 기도 알림을 보내는 자동 작업의 암호를
  주소창 형태(`?secret=...`)로도 받을 수 있습니다.
- **왜 중요한가**: 주소는 서버 접속 기록 등에 그대로 남기 쉬워 **암호가 로그에 노출**될 수 있습니다.
- **무엇을 하면 되나**: 암호는 주소가 아니라 "헤더"로만 받도록 제한합니다.
  (참고: 암호가 설정 안 됐을 때는 동작을 막아두어 이 부분은 안전하게 처리돼 있습니다.)

### 🟡 2-5. 외부 접근 허용 범위가 넓음 (CORS `*`)

- **문제**: API가 모든 외부 사이트의 호출을 허용하도록 열려 있습니다.
- **참고**: 로그인 토큰으로 신원을 확인하므로 **현재 설계상 곧바로 위험하진 않습니다.**
  다만 보안을 더 단단히 하려면 우리 앱 주소만 허용 목록에 넣는 것이 좋습니다.

## 3. 미완성 · 문서 불일치

### 🟠 3-1. 안내 문서가 옛 AI(OpenAI) 기준으로 남아 있음

- **문제**: `README.md` 등 문서가 **OpenAI(gpt-4o-mini), `OPENAI_API_KEY`** 기준으로
  적혀 있는데, **실제 코드는 Anthropic Claude**를 사용합니다.
- **왜 중요한가**: 새로 합류하는 운영자가 문서대로 `OPENAI_API_KEY`만 넣으면
  **앱이 동작하지 않습니다.** (실제 필요한 값은 `ANTHROPIC_API_KEY`)
- **무엇을 하면 되나**: `README.md`의 환경변수 안내를 Anthropic 기준으로 통일합니다.
  (참고: `README_DEPLOY.md`는 이미 Anthropic 기준으로 올바르게 적혀 있어, 문서끼리도 서로 다릅니다.)

### 🟠 3-2. 안내 문서가 가리키는 `.env.example` 파일이 없음

- **문제**: 문서는 `.env.example`을 복사해 시작하라고 안내하지만, **그 파일이 저장소에 없습니다.**
- **무엇을 하면 되나**: 필요한 환경변수 목록이 담긴 `.env.example` 예시 파일을 추가합니다.

### 🟡 3-3. 과거 장애 진단 문서가 남아 있음

- `DIAGNOSTIC_SSR_ERROR.md`는 과거 배포 장애(흰 화면 오류)를 다룬 진단 문서입니다.
  현재 해결되었는지 확인하고, 끝난 이슈라면 문서를 정리하거나 "해결됨" 표시를 권합니다.

## 4. 코드 품질 · 안정성

### 🟠 4-1. 배포 시 오류 검사를 끄는 설정

- **문제**: 빌드(배포 준비) 단계에서 **타입 오류와 코드 점검(린트)을 무시**하도록 설정돼 있습니다.
  (`typescript.ignoreBuildErrors: true`, `eslint.ignoreDuringBuilds: true`)
- **왜 중요한가**: 오류가 있어도 그대로 배포되어, **버그가 사용자에게 노출될 위험**이 커집니다.
- **무엇을 하면 되나**: 점진적으로 오류를 해결한 뒤 이 무시 설정을 끄는 것을 목표로 합니다.

### 🟠 4-2. 자동화 테스트 · CI가 전혀 없음

- **문제**: 코드가 바뀔 때 자동으로 검증해 주는 **테스트와 자동 점검(CI) 장치가 없습니다.**
- **왜 중요한가**: 수정할 때마다 기존 기능이 망가졌는지 사람이 일일이 확인해야 하며,
  실수가 그대로 배포될 수 있습니다.
- **무엇을 하면 되나**: 핵심 기능(로그인, 채팅, 알림)부터 간단한 테스트와
  GitHub 자동 점검을 도입합니다.

### 🟡 4-3. 매 응답마다 AI를 두 번 호출 (비용·속도)

- **문제**: 채팅 답변을 줄 때마다, 대화 기억을 갱신하기 위해 **AI를 한 번 더 호출**합니다.
- **왜 중요한가**: 매 메시지의 **비용과 응답 지연이 약 2배**가 될 수 있습니다.
- **무엇을 하면 되나**: 기억 갱신을 매번이 아니라 "몇 번에 한 번" 또는 백그라운드로
  처리하도록 바꾸면 비용·속도를 아낄 수 있습니다.

### 🟢 4-4. 정리하면 좋은 부분

- 빌드 임시 파일(`tsconfig.tsbuildinfo`)이 저장소에 포함 → 제거 권장.
- 코드 곳곳에 `any`(아무 타입) 사용이 많음 → 점진적으로 구체 타입으로 보강하면 버그가 줄어듭니다.

## 5. 가장 중요한 운영 이슈: 위기 감지 다국어 공백 🔴

- **문제**: 사용자가 자살·자해·학대 등 **위기 신호**를 보내면 도움 안내 카드를 띄우는
  기능이 있는데, 이 감지가 **한국어와 영어에서만** 작동합니다.
  (앱은 한국어·영어·태국어·스페인어·포르투갈어·힌디어·중국어 **7개 언어**를 지원합니다.)
- **왜 중요한가**: 나머지 5개 언어 사용자가 위급한 상황을 표현해도
  **도움 안내가 뜨지 않을 수 있습니다.** 생명과 직결되는 기능이라 영향이 큽니다.
- **무엇을 하면 되나**: 지원하는 7개 언어 모두에 대해 위기 신호 감지를 추가하고,
  안전하게 서버 단계에서도 한 번 더 확인하는 구조를 권합니다.

## 6. 다음에 하면 좋을 일 (우선순위)

### 1순위 — 출시 전 반드시 (안전·비용 사고 예방)
1. **`.gitignore` 추가** 및 잘못 올라간 파일 정리 → 비밀키 유출 방지 (2-1)
2. **위기 감지를 7개 언어로 확대** → 모든 사용자 안전 보장 (5)
3. **AI 호출 횟수 제한 + 이미지 크기 제한** → 비용 폭증·악용 방지 (2-2, 2-3)
4. **환경변수 문서 정정 + `.env.example` 추가** → 배포 실패 예방 (3-1, 3-2)

### 2순위 — 출시 직후 (안정성 강화)
5. **핵심 기능 테스트 + 자동 점검(CI) 도입** (4-2)
6. **빌드 오류 무시 설정 제거를 목표로 타입 오류 정리** (4-1)
7. **알림 크론 비밀값을 헤더 전용으로 제한** (2-4)

### 3순위 — 여유 있을 때 (개선)
8. **대화 기억 갱신 방식 최적화**로 비용·속도 절감 (4-3)
9. **CORS 허용 범위를 우리 앱 주소로 축소** (2-5)
10. **과거 진단 문서 정리**, `any` 타입 점진 보강 (3-3, 4-4)

## 7. 점검 범위 안내

- 점검 대상: 서버 API(채팅·알림·푸시), 인증·미들웨어, 데이터베이스 설정(SQL),
  서비스워커(오프라인/푸시), 주요 라이브러리, 배포·환경 설정 문서.
- 점검 방식: 코드 직접 검토. **실제 코드 수정은 하지 않았으며**, 이 리포트는 진단·제안용입니다.
- 작성: main 기준 새 작업 브랜치에서 리포트 파일만 추가했습니다.

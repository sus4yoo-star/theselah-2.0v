# 셀라(SELAH 2.0) 주간 점검 리포트 — 2026년 6월 4일

> 이 문서는 **개발을 모르는 분도 이해할 수 있도록** 쉬운 말로 정리한 주간 코드 점검 결과입니다.
> 코드는 **수정하지 않았고**, 점검 결과(무엇이 좋고, 무엇을 손봐야 하는지)만 담았습니다.

---

## 1. 한눈에 보는 요약

셀라는 "AI가 함께하는 기독교 정서 지원 + 성경 묵상" 앱입니다.
현재 코드는 **기본 골격이 탄탄하고, 보안의 핵심(사용자별 데이터 격리)은 잘 지켜져** 있습니다.
다만 **출시·운영 단계에서 "돈이 새거나(비용)", "실수로 비밀정보가 노출되거나", "버그가 그대로 배포되는"** 것을 막는 안전장치가 아직 부족합니다.

| 구분 | 상태 | 한 줄 평가 |
|------|------|-----------|
| 사용자 데이터 보호(개인정보 격리) | 🟢 양호 | 사용자는 자기 데이터만 보도록 잘 설정됨 |
| 비밀키 관리 | 🟢 양호 | 비밀번호·API 키가 코드에 노출되어 있지 않음 |
| 비용(AI 사용료) 보호장치 | 🔴 주의 | 무제한으로 호출될 수 있어 요금 폭증 위험 |
| 실수 방지 장치(빌드 검사 등) | 🟡 보완 필요 | 버그가 걸러지지 않고 배포될 수 있음 |
| 테스트(자동 점검 코드) | 🔴 없음 | 자동으로 품질을 확인하는 코드가 전혀 없음 |

## 2. 이번 주 새로 확인한 점검 항목

코드를 훑어 **버그·미완성·개선점·보안 이슈**를 점검했습니다.
각 항목에 **중요도(P0 가장 급함 → P2 천천히)**를 붙였습니다.

### 🔴 P0 — 출시 전에 꼭 처리하면 좋은 것

**[P0-1] AI 호출에 "사용량 제한"이 없습니다 → 요금 폭증 위험**
- 로그인한 사용자라면 채팅을 **무제한으로** 보낼 수 있고, 그때마다 AI(Claude)에 요청이 갑니다.
- 게다가 **메시지 한 번에 AI를 두 번 호출**합니다. (① 실제 답변 ② "장기 기억" 업데이트)
  즉, 실제 사용료가 생각보다 **약 2배**로 나갈 수 있습니다.
- 악의적인 사용자나 자동 프로그램이 채팅을 폭주시키면 **AI 요금이 통제 불가능하게 늘어날 수 있습니다.**
- 👉 제안: 사용자/시간당 메시지 횟수 제한(예: 분당 N회)을 두고, AI 사용료 알림(예산 알림)을 설정하세요.
  관련 위치: `src/app/api/chat/route.ts`, `src/lib/selah-memory.ts`

**[P0-2] `.gitignore` 파일이 없습니다 → 실수로 비밀정보가 공개될 위험**
- 보통 프로젝트에는 "이 파일들은 절대 업로드하지 마"라는 목록(`.gitignore`)이 있는데, **이 저장소에는 그 파일이 아예 없습니다.**
- 이 상태에서는 비밀키가 담긴 `.env` 파일 등을 **실수로 그대로 업로드할 위험**이 큽니다.
  (실제로 빌드 임시파일 `tsconfig.tsbuildinfo`가 이미 같이 올라가 있습니다 — 불필요한 파일입니다.)
- 👉 제안: `.gitignore`를 만들어 `.env*`, `node_modules`, `.next`, `out`, `tsconfig.tsbuildinfo` 등을 제외 처리하세요.
  *(다행히 현재 비밀키가 코드에 노출된 흔적은 없습니다.)*

### 🟡 P1 — 곧 처리하면 좋은 것

**[P1-1] 빌드할 때 "오류 검사"를 꺼두었습니다 → 버그가 그대로 배포될 수 있음**
- 설정상 **타입 오류와 코드 스타일 오류가 있어도 빌드가 성공**하도록 되어 있습니다. (`ignoreBuildErrors`, `ignoreDuringBuilds`)
- 마치 "자동차 경고등을 꺼둔 채 운전"하는 것과 같아, **명백한 버그도 사용자에게 그대로 나갈 수 있습니다.**
- 👉 제안: 최소한 타입 오류는 빌드를 막도록 켜두는 것을 권장합니다. (위치: `next.config.mjs`)

**[P1-2] 첨부 이미지 용량 제한이 없습니다 → 서버 부담·비용 증가**
- 사용자가 채팅에 이미지를 첨부할 수 있는데, **이미지 크기에 상한이 없습니다.**
- 아주 큰 이미지를 보내면 서버 메모리·처리시간·AI 비용이 크게 늘 수 있습니다.
- 👉 제안: 첨부 이미지 용량 상한(예: 5MB)을 두세요. (위치: `src/app/api/chat/route.ts`)

**[P1-3] 자동 점검 코드(테스트)가 전혀 없습니다**
- 코드가 잘 동작하는지 **자동으로 확인하는 장치가 하나도 없습니다.**
- 기능이 늘어날수록 "한 곳을 고치면 다른 곳이 깨지는" 사고를 잡기 어려워집니다.
- 👉 제안: 핵심 로직(로그인 확인, 알림 발송 시간 계산 등)부터 간단한 테스트를 추가하세요.

**[P1-4] AI 사용량 비밀번호(CRON_SECRET)를 주소창(URL)로도 받을 수 있습니다**
- 알림 발송용 자동 작업의 비밀번호를 헤더뿐 아니라 **인터넷 주소(URL) 뒤에 붙여서도** 받습니다.
- URL은 서버·중계 장비 로그에 그대로 남는 경우가 많아 **비밀번호가 로그에 노출될 수 있습니다.**
- 👉 제안: URL 방식은 막고, 헤더 방식만 허용하세요. (위치: `src/app/api/cron/send-reminders/route.ts`)

### 🟢 P2 — 여유 있을 때 다듬으면 좋은 것

- **[P2-1] 답변 후 "기억 저장"이 끝날 때까지 응답 연결이 유지됩니다.** → 사용자가 체감하는 응답 완료가 약간 늦어질 수 있습니다. ("기억 저장"을 응답과 분리하면 더 빠르게 느껴집니다.) 위치: `src/app/api/chat/route.ts`
- **[P2-2] 데이터베이스 설정 파일 위치가 제각각입니다.** → `user_memories` 설정만 다른 폴더(`supabase/001_user_memories.sql`)에 있어, 일괄 적용 시 빠질 수 있습니다. 한 폴더(`supabase/migrations/`)로 모으길 권장합니다.
- **[P2-3] 사용자가 고른 언어를 자동 언어감지가 덮어씁니다.** → 짧은 문장에서 엉뚱한 언어로 답할 가능성이 있습니다. 위치: `src/lib/i18n.ts`, `src/app/api/chat/route.ts`
- **[P2-4] 오류 메시지에 외부 시스템의 상세 오류가 그대로 노출됩니다.** → 사용자에게는 간단한 안내만 보여주는 편이 안전합니다.

## 3. 잘 되어 있는 점 (칭찬할 부분)

점검 중 **이미 잘 갖춰진** 부분도 확인했습니다. 유지하면 좋습니다.

- ✅ **개인정보 격리가 탄탄합니다.** 데이터베이스에 "사용자는 자기 데이터만 볼 수 있다"는 규칙(RLS)이 채팅·알림·기억 모든 테이블에 적용돼 있습니다.
- ✅ **로그인하지 않으면 AI를 쓸 수 없습니다.** API 키가 함부로 쓰이지 않도록 막혀 있습니다.
- ✅ **비밀키가 코드에 노출돼 있지 않습니다.** (관리자 키, AI 키 모두 환경변수로 관리)
- ✅ **모바일 앱·웹 양쪽 로그인을 모두 안전하게 처리**하도록 신경 쓴 흔적이 보입니다.
- ✅ **알림(푸시)에서 죽은 기기 구독을 자동 정리**하는 등 운영 디테일이 들어가 있습니다.

## 4. 출시·운영 관점: 다음에 하면 좋은 일 (우선순위)

> "지금 무엇부터 하면 가장 도움이 될까?"에 대한 추천 순서입니다.

1. **(가장 먼저) AI 사용료 안전장치 만들기** — 사용량 제한 + 예산 알림. *돈이 새는 것을 막는 일* → [P0-1]
2. **`.gitignore` 추가하고 불필요한 파일 정리** — *비밀정보 유출 사고 예방* → [P0-2]
3. **빌드 오류 검사 다시 켜기** — *버그가 그대로 배포되는 것 방지* → [P1-1]
4. **이미지 용량 제한 추가** — *서버 부담·비용 보호* → [P1-2]
5. **핵심 기능 자동 테스트 추가** — *기능이 늘어도 안정적으로 유지* → [P1-3]
6. **알림 비밀번호 노출 경로 제거** — *운영 보안 강화* → [P1-4]
7. (여유 시) 응답 속도 체감 개선·DB 설정 정리 등 P2 항목 → 3장 참고

## 5. 이번 점검 범위 / 한계

- **점검 방식:** 저장소 전체 코드를 사람이 읽어 내려가며 보안·버그·미완성·개선점을 살폈습니다.
- **포함:** 서버 API(채팅·알림·구독), 로그인/세션 처리, 데이터베이스 보안 규칙, 설정 파일.
- **이번에 깊게 다루지 않은 것:** 화면(UI) 컴포넌트의 세부 동작, 실제 서비스 환경에서의 부하·성능 측정.
- 이 리포트는 **코드를 고치지 않은 진단 보고서**입니다. 실제 수정은 위 우선순위에 따라 별도로 진행하시길 권합니다.

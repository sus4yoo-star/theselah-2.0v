## 점검 범위

이번 주에 살펴본 항목:

- **채팅 API** (`/api/chat/route.ts`): Claude와 실시간 대화하는 핵심 기능
- **기도 알림 API** (`/api/reminders`, `/api/cron/send-reminders`): 매일 정해진 시간에 알림 발송
- **푸시 알림 API** (`/api/push/*`): 기기에 알림 보내는 기능
- **속도 제한 모듈** (`/src/lib/rate-limit.ts`): 신규 추가된 방어 코드
- **AI 메모리 모듈** (`/src/lib/selah-memory.ts`): 대화 기억 저장
- **위기 감지 모듈** (`/src/lib/crisis-detect.ts`, `feature-strings.ts`): 자살·위기 키워드 감지
- **로그인·인증** (`middleware.ts`, `supabase/api-auth.ts`): 사용자 계정 보호
- **데이터베이스 보안** (`supabase/*.sql`): 행 수준 보안 정책
- **서비스워커·PWA** (`public/manifest.json`): 오프라인 및 앱 설치
- **배포 설정·문서** (`README_DEPLOY.md`, `netlify.toml`, `*.md`)
- **의존성 보안** (`package.json`): npm 취약점 감사

#### 1. 배포 안내 문서에 "OpenAI" 레거시 표현 3곳 잔존

**무엇이 문제인가요?**  
`README_DEPLOY.md` 파일 4번째·13번째·112번째 줄에 현재 앱이 "OpenAI"를 사용한다고 적혀 있습니다. 하지만 앱은 지난해 Anthropic(Claude)으로 전환됐으며, 실제 환경변수도 `ANTHROPIC_API_KEY`입니다. 또한 같은 문서에 "Next.js 15" 라고 적혀 있으나 실제 버전은 16입니다.

```
4번째 줄: "Supabase · OpenAI and deployable to…"
13번째 줄: "An OpenAI API key with billing enabled → platform.openai.com"
112번째 줄: "api/chat/route.ts  server-only OpenAI proxy (streaming)"
```

**왜 중요한가요?**  
처음 서버를 설정하는 사람이 이 문서를 보고 OpenAI API 키를 발급받아 설정하면 앱이 전혀 작동하지 않습니다. 원인을 찾는 데 30분~1시간을 낭비할 수 있습니다.

**무엇을 하면 되나요?**  
`README_DEPLOY.md`에서 "OpenAI" 세 곳을 "Anthropic"으로 수정하고, "Next.js 15"를 "16"으로 변경합니다. (약 15분 작업)

### 🟡 보통

#### 2. 오류가 나도 개발팀이 알 수 없음 (미해결, 3주 연속)

**무엇이 문제인가요?**  
AI 메모리 저장 실패, 외부 API 오류, 푸시 발송 오류가 발생해도 시스템이 조용히 넘어갑니다. 코드에는 빈 `catch {}` 블록이 여러 곳에 있습니다.

**왜 중요한가요?**  
사용자의 대화 내용이 저장되지 않거나, 채팅이 은밀히 실패하고 있어도 운영팀이 모릅니다. 문제가 며칠째 지속돼도 사용자 불만이 접수되기 전까지 발견이 어렵습니다.

**무엇을 하면 되나요?**  
Sentry(무료 플랜 지원) 또는 Netlify 함수 로그 활성화로 최소한의 오류 기록 체계를 만듭니다. 3주째 미해결 상태이므로 이번 주 내 조치를 권장합니다.

---

#### 3. 기도 알림 Cron 작업 모니터링 없음 (미해결, 3주 연속)

**무엇이 문제인가요?**  
매일 기도 알림을 발송하는 자동 작업이 실패해도 개발팀이 감지할 방법이 없습니다. 성공·실패 횟수를 기록하거나 연속 실패 시 알림을 보내는 체계가 없습니다.

**왜 중요한가요?**  
사용자가 매일 기대하는 기도 알림이 며칠 동안 오지 않아도 운영팀이 먼저 알기 어렵습니다. 사용자 불만이 쌓인 뒤에야 문제를 파악하게 됩니다.

**무엇을 하면 되나요?**  
Cronitor, Better Uptime, UptimeRobot 등 무료 Cron 모니터링 서비스를 연결합니다. 성공 시 "heartbeat" 신호를 보내도록 `/api/cron/send-reminders`에 한 줄 추가하면 됩니다. 3주째 미해결이므로 이번 주 내 조치를 권장합니다.

---

#### 4. 속도 제한이 서버리스 환경에서 완전히 동작하지 않을 수 있음 (신규)

**무엇이 문제인가요?**  
이번 주에 새로 추가된 API 속도 제한 기능(`rate-limit.ts`)은 서버 메모리 내에서 카운트를 관리합니다. 그런데 Netlify 서버리스 환경에서는 요청마다 다른 서버 인스턴스(컴퓨터)에서 실행될 수 있어, 각 인스턴스가 별도로 카운트를 셉니다. 예를 들어 인스턴스가 5개라면 실제로는 1분에 100번(20×5)까지 보낼 수 있게 됩니다.

코드에 이 한계가 영어 주석으로 명시돼 있습니다 (`rate-limit.ts` 14번째 줄).

**왜 중요한가요?**  
갑작스러운 사용량 급증(스크립트 공격) 상황에서 제한이 의도한 대로 작동하지 않을 수 있어, API 비용 폭탄 방지 효과가 약해집니다. 현재 트래픽 수준에서는 큰 문제가 아니지만, 서비스 성장 시 위험해질 수 있습니다.

**무엇을 하면 되나요?**  
Upstash Redis (서버리스 친화적, 무료 플랜 있음) 또는 Supabase 테이블로 카운트 저장소를 이전하면 모든 인스턴스가 같은 카운터를 공유할 수 있습니다. 지금 당장 급하진 않으나 서비스 확장 전 개선이 필요합니다.

---

#### 5. 메모리 업데이트에 비싼 AI 모델 사용 중 (미해결, 3주 연속)

**무엇이 문제인가요?**  
사용자와 대화할 때마다 Claude API가 두 번 호출됩니다. 첫 번째는 실제 대화 답변(claude-sonnet), 두 번째는 이전 대화를 요약해 저장하는 메모리 업데이트(역시 claude-sonnet)입니다. 메모리 업데이트는 단순 요약 작업이라 저렴한 모델(claude-haiku, 약 80% 저렴)로 충분합니다.

**왜 중요한가요?**  
사용자가 많아질수록 매달 나가는 API 비용의 약 30~40%가 메모리 업데이트에서 발생합니다. 같은 품질을 절반 이하 비용으로 유지할 수 있는 개선입니다.

**무엇을 하면 되나요?**  
`selah-memory.ts`의 `updateUserMemory` 함수에서 메모리 전용 경량 모델을 사용하도록 변경합니다. 예: `const MEMORY_MODEL = "claude-haiku-4-5"`. 대화 품질에는 영향이 없습니다.

#### 6. 데이터베이스 설치 안내가 3개 파일에 흩어져 불명확 (미해결)

**무엇이 문제인가요?**  
새 서버에 앱을 배포할 때 데이터베이스 테이블을 만들어야 하는데, 그 절차가 세 개 파일(`README_DEPLOY.md`, `PRAYER_REMINDERS_SETUP.md`, `001_user_memories.sql` 주석)에 흩어져 있고 순서가 불명확합니다. 특히 `README_DEPLOY.md`는 첫 번째 마이그레이션 파일(`0001_init.sql`)만 언급하고, 사용자 메모리 테이블(`001_user_memories.sql`)과 기도 알림 테이블(`20260527_prayer_reminders.sql`)은 별도로 실행해야 한다는 내용이 명확하지 않습니다.

**왜 중요한가요?**  
배포 담당자가 단계를 놓치면 메모리 기능이나 기도 알림 기능이 조용히 작동하지 않습니다. 사용자는 앱을 사용할 수 있지만 핵심 기능이 빠진 상태로 운영됩니다.

**무엇을 하면 되나요?**  
`README_DEPLOY.md`에 "Step 1b"를 3단계로 명확히 분리합니다:
1. `supabase/migrations/0001_init.sql` (채팅 테이블)
2. `supabase/001_user_memories.sql` (AI 메모리 테이블)
3. `supabase/migrations/20260527_prayer_reminders.sql` (기도 알림 테이블)

#### 7. 푸시 알림 발신자 이메일이 구버전 회사 주소로 하드코딩

**무엇이 문제인가요?**  
푸시 알림 발송 모듈(`push-server.ts` 15번째 줄)에서 발신자 이메일의 기본값이 `"mailto:hello@amov.kr"`로 설정되어 있습니다. AMOV는 이전 회사/브랜드 이름으로, `VAPID_SUBJECT` 환경변수를 설정하지 않으면 이 주소가 사용됩니다.

**왜 중요한가요?**  
환경변수를 설정하지 않은 배포자는 자신도 모르게 다른 회사 이메일로 푸시 알림을 보내게 됩니다. 브랜드 혼란 및 잘못된 발신자 정보가 생깁니다.

**무엇을 하면 되나요?**  
기본값을 빈 문자열로 변경하고 `VAPID_SUBJECT`가 없으면 경고를 남기거나, `README_DEPLOY.md`의 필수 환경변수 목록에 `VAPID_SUBJECT`를 추가합니다.

## 이번 주 긍정적 발견사항

지난주 이후 눈에 띄는 개선이 이루어졌습니다:

- **API 속도 제한**: 사용자별 1분당 20회 제한 구현, 테스트 코드도 완비

- **CI 파이프라인 추가**: 모든 브랜치·PR에 타입 검사·린트·유닛 테스트·빌드 자동 실행

- **보안 구조 유지**: Supabase RLS, Bearer/쿠키 이중 인증, 환경변수 관리 모두 양호
